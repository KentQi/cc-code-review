## 0. 一句话结论

**1.18.1–1.18.3 把前两轮的 20 条 P0/P1 基本修对了，架构与工程品味仍在平均线之上；但 1.18.4 这一轮"清 P2/P3  backlog"同时引入了新的攻击面，而核心防御（git 配置加固）仍然是"逐个键黑名单"而非"机制性封堵"——本轮因此又找到 7 条可实测的 P0，其中 3 条是仓库可控的任意命令执行。**

## 2. P0 — 必须修（7 条）

### P0-1 `protocol.ext.allow` 不在子进程 git 加固清单里 → 仓库可控 RCE

**文件**：`src/claude.js:429`（`buildClaudeEnv()` 的 `gitOverrides`）
**状态**：✅ Lead 实测复现（标记文件被创建）

代码自己的注释（`src/claude.js:417-428`）把威胁说得很清楚：

> GIT_CONFIG_* … follows git into the claude child and into every Bash tool call it makes. That is the layer the scanner below cannot be: `.git/config` can name a command the scan did not anticipate, and **`git remote show origin` (allowlisted, and suggested by the prompt) runs core.sshCommand before any network I/O**.

清单中和这条威胁对应的键有 7 个：`core.sshCommand`、`core.fsmonitor`、`core.pager`、`core.hooksPath`、`diff.external`、`credential.helper`、`core.attributesFile`。**`protocol.ext.allow` 不在其中。**

它只出现在 `GIT_HARDENING_ARGS`（`src/claude.js:2000`），而那个数组只 prepend 到**服务器自己**的 git 调用（`src/claude.js:2157`、`:2820`），永远不会进入 claude 子进程。

复现链（全部实测）：

1. 被审仓库 `.git/config`：
   ```ini
   [remote "origin"]
       url = ext::touch /tmp/acr5/lead/PWNED
   [protocol "ext"]
       allow = always
   ```
2. `repoRunsGitPrograms(repo)` → **`{"refusals":[],"notes":[]}`** —— 扫描器声明仓库干净。`CONFIG_EXEC_KEYS`（`src/claude.js:2099`）不含 `protocol.ext.allow`；整个 `src/claude.js` 对 `ext::`、`remote.origin.url`、`insteadOf` 的命中数为 **0**。
3. `analyseCommand("git remote show origin", {repoRoot})` → **`{"ok":true,"chained":false}`** —— guard 放行。
4. 提示词**主动建议**这条命令：`src/prompt.js:246` 与 `:270`（"detect it with `git rev-parse --abbrev-ref origin/HEAD`, falling back to `git remote show origin`"），`assets/skills/code-review/SKILL.md:78` 把 `git remote -v|get-url|show` 列入执行契约。
5. 用 `buildClaudeEnv()` 的真实输出跑 `git remote show origin`：
   ```
   exit 128 stderr: fatal: Could not read from remote repository. ...
   MARKER created? -> *** YES — ARBITRARY COMMAND EXECUTED ***
   ```
6. 对照组：同一条命令加服务器自己的 `-c protocol.ext.allow=never` → `fatal: transport 'ext' not allowed`（被挡）。证明缺的就是这一个键。

**修复方向**：把 `protocol.ext.allow=never`（以及 `protocol.file.allow=never`、`url.*.insteadOf`、`remote.*.vcs`）并入 `gitOverrides`，让 `gitOverrides` 与 `GIT_HARDENING_ARGS` 由**同一张表**生成（见 P2-1）。

### P0-2 `.git/config.worktree` 在主工作树下从不被扫描 → 仓库可控 RCE

**文件**：`src/claude.js:2382-2383`（`repoConfigFiles()` 主工作树分支）
**状态**：✅ 独立验证者 CONFIRMED，附对照组 + 标记文件

主工作树分支只枚举 `.git/config`：

```js
if (st && st.isDirectory()) {
  walk(path.join(gitDir, "config"), ".git/config", 0, [repoPath, gitDir]);
```

`config.worktree` 只在 `else if (st)` 分支里读（`:2399-2400`），而那个分支只在 `.git` 是**文件**（linked worktree / submodule）时进入。

而 git 在主工作树、`extensions.worktreeConfig=true` 时**确实**读 `.git/config.worktree`（实测 `git config --list --show-origin` → `file:.git/config.worktree diff.evil.textconv=...`）。于是仓库放一个 `[diff "evil"] textconv = /tmp/evil.sh` 在 `.git/config.worktree`、`.gitattributes` 写 `*.txt diff=evil`，`repoRunsGitPrograms()` 返回 `{"refusals":[],"notes":[]}`，评审照常开始，评审 agent 的第一个 `git diff` / `git log -p` / `git show` 就执行了它（标记文件已创建）。

子进程环境无法缓解：`GIT_CONFIG_KEY_n` 是**完整字面键**匹配，无法通配 `diff.<name>` 这个 subsection——7 个 override 里只有 `diff.external`，是不同的键。验证者在 `buildClaudeEnv()` 下端到端跑 `git diff`，驱动仍然执行。

**对照组**（证明根因是文件枚举）：同一驱动放到 `.git/config` → refusal；放到 linked worktree 的 `config.worktree` → refusal；放到主工作树的 `.git/config.worktree` → **无 refusal**。

**修复方向**：不要手工枚举配置文件位置。在仓库内跑一次 `git config --list --show-origin -z`（带加固 env），对任何 repo 可控的 origin 文件拒绝，然后评估来自它的每个 key/value。这一改同时覆盖主/链接工作树、`commondir`、`config.worktree`、`includeIf`。

### P0-3 `.gitattributes` 遍历跳过 `node_modules/` → 仓库可控 RCE

**文件**：`src/claude.js:2521`（`repoAttributeFiles()`）
**状态**：✅ 独立验证者 CONFIRMED，附对照组 + 标记文件

```js
// .git (also a FILE in a worktree) and node_modules are never reviewed
// content; descending them would only slow the pre-spawn scan down.
if (e.name === ".git" || e.name === "node_modules") continue;
```

注释给的是一次纯性能理由。但 git 对**文件路径上的每一层目录**都应用 `.gitattributes`，包括 `node_modules/`。实测：仓库提交 `node_modules/.gitattributes`（`*.txt diff=evil`）+ `node_modules/pkg/a.txt` + `.git/config` 的 `[diff "evil"] textconv = /tmp/evil.sh`：

```
$ git check-attr diff -- node_modules/pkg/a.txt
node_modules/pkg/a.txt: diff: evil
$ git log -p -1
textconv EXECUTED: YES
$ node probe.mjs   # repoRunsGitPrograms
{ "refusals": [], "notes": [] }
```

**对照组**：同样的内容放在 `src/.gitattributes` → `refusals: ["src/.gitattributes: *.txt diff=evil (driver \"evil\" is defined in the repo's git config)"]`。证明根因就是这次剪枝。

注意一个细节：在评审 agent 自己的环境里，裸 `git diff` 会因空的 `diff.external=` 覆盖而 `fatal: external diff died`，所以 RCE 实际经由 `git log -p` / `git show` 落地——两者都在 allowlist 里，也都是评审最先跑的命令。

**修复方向**：从 git 推导生效的 attributes，而不是走目录树——对将要被 diff 的路径跑 `git check-attr --all -- <paths>`；并且把"有一个 attribute 文件我们没读到"当作 refusal，而不是当作"没有引用"。

### P0-4 `git blame --cont`（`--contents` 的缩写）读取宿主任意文件全文

**文件**：`src/shell-guard.js:363-367`（`OUTRIGHT_DENY.git`）+ `:421`（git 豁免路径检查）
**状态**：✅ Lead 与验证者双向 CONFIRMED，真实 git 打印出文件全文

  git: {
    "--no-index": "`git diff --no-index` reads arbitrary paths outside the repository",
    "--contents": "`git blame --contents` reads an arbitrary file outside the repository",
    "-X": "`git ls-files -X` reads a path list from an arbitrary file outside the repository",

00000000 (External file (--contents) 2026-10-30 00:20:35 +0800 1) AKIAIOSFODNN7EXAMPLE

`--cont` / `--content` / `--cont=FILE` 全部放行并打印**文件全文**。guard 自己的拒绝消息（"`git blame --contents` reads an arbitrary file outside the repository"）等于在告诉攻击者该缩写成什么。

另有两个门禁设计问题值得单独记：`.github/workflows/ci.yml`（本地在途版）用 `CLAUDE_CODE_PATH` 指向 stub，使 `resolveClaudeCli()` 的优先级 2–4（PATH 扫描、知名安装位置、npm root 回退）在 CI 上**永不执行**，而唯一不覆盖它的 `cancel-test.mjs` 是被排除的付费套件；本地 `npm test` 的 cross-cases C1 实际在跑真实 CLI（日志显示 `prewarm done: /Users/kent/.local/bin/claude`），CI 却打的是 stub——两侧测的不是同一条路径。

**CI 矩阵与 `engines` 脱节**：本地在途 `ci.yml:23` 把矩阵从 PR #4 head 的 `node: [18, 22]` 改成 `[20, 22, 24]`，而 `package.json:57` 仍声明 `"node": ">=18.19"`、README 徽章仍写 `node ≥18.19`。`npm ci` 不强制 engines，于是**声明支持的最低运行时版本没有任何 CI 任务跑过**（且 Node 18 已于 2025-04-30 EOL）。这是纯工作树改动——PR #4 head 的 ci.yml 仍是 `[18, 22]`，覆盖是被这次未提交的修改移除的。
